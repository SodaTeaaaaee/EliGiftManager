# V2 业务边界

> V2 必须覆盖的业务范围、生命周期和明确不解决的问题。
> 当前代码已按这些边界实现。

## 3. V2 业务边界

### 3.1 两类需求并存

V2 同时支持：

1. **会员权益型**（`membership_entitlement`）：有身份，可能无订单号，需求由规则推导。权益判定权威未必属于本系统。
2. **零售订单型**（`retail_order`）：有订单，可能无会员身份，商品需求通常在外部订单已明确。

同一平台可同时拥有两种业务面（如 Bilibili 的直播支持 vs 创作者商品）。

### 3.1.0 不是"平台二分法"

区分的是需求类型和履约语义差异，不是把平台刚性分成两类。`source_channel` + `source_surface` 是正确的建模维度。

### 3.1.1 新需求的 7 个业务点

1. **第二类消费者**：系统同时处理"有身份无订单的会员"和"有订单无身份的买家"
2. **第二类上游来源**：除会员名单外，还有零售订单、手工补录、未来 API
3. **工厂导出不再是终点**：还需等待发货回传和来源渠道回填
4. **物流回传和映射**：工厂回传数据需映射转换后回填上游渠道
5. **回填结果追踪**：区分"已发货/已回填/回填失败"等状态
6. **混合波次**：同一波次可同时包含会员赠礼、商城订单、人工补发
7. **领取参数补全**：会员权益可能需要补充地址、尺码、款式等才能进入履约

### 3.1.2 对旧模型的 5 个直接冲击

| 旧假设 | 现状 |
|--------|------|
| 履约对象 ≈ 会员 | 买家可能没有会员身份 |
| 需求来源只有"名单" | 零售来源是"订单" |
| `DispatchRecord` 终点是导出 CSV | 工厂发货与回填发生在导出之后 |
| 一个 `status` 字段够用 | 至少需要地址/工厂提交/发货/回填 4 个维度 |
| "已导出"= 结束 | "已导出"只是流程中段 |

### 3.1.3 典型业务场景

- **场景 A（纯会员回馈）**：会员名单 → 规则推导 → 绑定地址 → 导出工厂 → 工厂回传物流
- **场景 B（纯零售订单）**：订单表 → 解析订单行 → 生成履约行 → 导出工厂 → 回填来源渠道
- **场景 C（同平台双业务面）**：同平台不同业务面的数据进入同一波次，各自走不同分配路径
- **场景 D（混合波次）**：会员赠礼 + 商城订单 + 人工补发，行级保留来源可追踪
- **场景 E（会员限定购买）**：`retail_order` + `eligibility_context_ref`，不主动下单不产生待发

### 3.1.4 分配语义

| 语义 | 适用 | 特征 |
|------|------|------|
| `policy_driven` | 会员权益、活动回馈 | 由规则推导初始履约结果，允许修正 |
| `demand_driven` | 零售订单、手工补单 | 上游已是明确需求行，优先尊重原始订单 |

判断：不主动下单也欠用户应发物 → `policy_driven`；不主动下单就不出现待履约行 → `demand_driven`。

### 3.1.5 当前 tag 系统定位

当前 tag 系统是优秀的 `policy_driven` 分配系统，V2 保留其在会员权益场景的主导地位，不强迫零售订单先翻译成 tag。

### 3.1.6 会员体验不得退化（强约束）

1. 会员权益型波次仍可使用规则驱动分配
2. 批量加赠、减赠、覆盖能力不得明显退化
3. 不能为统一零售语义破坏当前会员分配体验

### 3.1.7 首版不把复杂多身份集合当硬需求

首版覆盖：单平台身份等级、`platform_all`、`wave_all`、显式用户覆盖。内部结构预留扩展位。
